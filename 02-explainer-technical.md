# Reckon — technical explainer

Payment-to-invoice reconciliation. Python 3.11, FastAPI, SQLAlchemy, Pydantic.
~7,900 lines of source across 47 modules, ~3,850 lines of tests (494 tests, 21
files), 36 commits. Paystack is the ingest adapter; matching, review and audit
work on a provider-agnostic record.

Every number below comes from `out/eval.json`, regenerated by `make eval`
(`src/recon/evaluation/harness.py`). `tests/test_readme.py` re-runs the harness
and fails if the README's quoted figures drift from it.

---

## 1. Architecture, stage by stage

### 1.1 Ingest — `recon/app.py` → `recon/ingest.py` → `recon/paystack/`

```
POST /webhooks/paystack
  → paystack/signature.py   verify_signature()   HMAC SHA-512 over raw bytes
  → ingest.receive()        writes WebhookEvent, PK = event_key   [idempotency]
  → HTTP 200                                                      [fast ack]
  → BackgroundTasks → ingest.process()
        → paystack/events.py  parse_event() / apply_event()
        → paystack/client.py  verify_transaction()               [authority]
        → models.py           Transaction, AuditRecord
```

Four things are load-bearing here:

- **Signature over raw bytes, not re-serialised JSON.** `signature.py` refuses a
  `str` input outright; `app.py` reads `await request.body()` before anything
  parses it. Comparison is `hmac.compare_digest`, and
  `tests/test_signature.py::test_comparison_is_constant_time` greps the source to
  stop someone "simplifying" it to `==`.
- **Idempotency by `event_key`**, built in `events.build_event_key()` from event
  type plus the most specific id in the payload, falling back to a body hash.
  `tests/test_ingest.py` replays Paystack's full retry schedule — 76 deliveries
  of one event — and asserts one `WebhookEvent`, one `Transaction`, one amount.
- **Forward-only state.** `enums.STATUS_RANK` gives pending=0, failed=10,
  success=20, reversed=30, refunded=40. `events._advance_status()` ignores
  anything that doesn't increase rank, so a `refund.processed` arriving before
  its `charge.success` is not undone by the late charge.
- **Verify is the authority.** `ingest._confirm_against_paystack()` overwrites
  amount and fees from the verify call. It distinguishes three outcomes:
  confirmed, "Paystack has no such reference" (→ `FAILED`, unverified), and "we
  couldn't ask" (→ unverified, retryable). Collapsing the last two is the bug
  this guards against.

### 1.2 Matching — `recon/match/`

`pipeline.py::Pipeline.run()` sorts payments oldest-first, runs the
deterministic layer over all of them, then the probabilistic layer over the
residual only, threading a `claimed` set so an invoice settled earlier is off the
table later.

**Layer one — `deterministic.py`.** Four exact rules, tried in order, none of
which fires when two candidates fit:

1. `_already_seen` — same amount + same normalised payer within 24h → not a new
   settlement, always to a human.
2. `_exact_reference` — `stated_reference` from structured metadata, or a
   reference-shaped token scraped from the narration
   (`\b([A-Z]{2,6}[-/ ]?\d{3,8})\b`) **and confirmed present in the ledger**, so
   a false positive would have to be character-for-character a live invoice
   number. Two distinct references found → declines.
3. `_dedicated_account` — DVA number → customer, and that customer has exactly
   one open invoice at exactly this amount.
4. `_amount_and_window` — exactly one unclaimed invoice at this exact amount,
   issued within `DEFAULT_WINDOW = 10 days` (and not after the payment).

**Layer two — the residual.** `candidates.py::shortlist()` builds ≤24 candidates
per payment via three routes (DVA owner, name-similar customers above
`NAME_FLOOR = 0.40`, anyone's invoice at this exact amount), plus *combinations*
of 2–3 of one customer's invoices summing to exactly the amount paid — the only
route that can catch a split payment. `features.py::extract()` produces 18 named
features; `model.py::LogisticModel` scores them; `calibration.py` maps the score
to a probability; `threshold.py` decides clear-or-queue.

The top learned weights (`models/model.json`):

| feature | weight |
|---|---:|
| `amount_closeness` | +2.678 |
| `overpaid` | −1.829 |
| `recency` | +1.613 |
| `name_similarity` | +1.215 |
| `paid_by_transfer` | −1.078 |
| `amount_exact` | +0.866 |
| bias | −2.072 |

**Name matching — `similarity.py`.** Four blended views: exact token overlap
(0.40), variant-folded overlap (0.20), per-token best-pair `difflib` ratio (0.25),
whole-string sorted-token ratio (0.15). Noise words (banks, `TRF`, `NIP`, `LTD`)
are stripped first.

### 1.3 Training — `recon/match/training.py`

`residual_rows()` → `split_by_time(dev_fraction=0.75)` → `out_of_fold_scores(folds=4)` →
`pick_calibrator()` → `best_per_payment()` → `choose_threshold()` → refit on all
dev data. Split is by **time**, not random, and whole payments stay on one side —
because `we_have_seen_this_payer_before` would otherwise leak a customer's
Tuesday payment into the model scoring their Wednesday one.

### 1.4 Unstructured intake — `recon/intake/`

`parse.py::Intake` runs `RuleExtractor` (regex + `amounts.py`, which parses
`₦45,000`, `45k`, `2.5m`, `forty-five thousand naira` without ever touching a
float), then optionally `anthropic_reader.py::AnthropicReader`. Both satisfy the
same `Extractor` protocol. Output is validated by `schema.py::PaymentReport`
(Pydantic, `extra="forbid"`). One attempt per layer, no retry loop.

The model layer uses `client.messages.parse()` with `output_format=ReportReading`
— schema generated from the Pydantic class, so what the model is told to produce
and what is accepted cannot drift. `readable: false` is a first-class answer.

### 1.5 Review and reporting — `recon/review/`, `recon/report/`

`queue.py::build()` sorts unresolved matches by money at risk descending.
`report/settlement.py` splits "taken today" from "received today" and never nets
them: `balances` asserts `cash_in_hand + still_in_the_air == net_earned`.
`audit.py` is insert-only.

### 1.6 Money — `recon/money.py`

Integer kobo throughout. `Money(1250.5)` raises; `bool` is rejected explicitly
because it subclasses `int`. `percent_bps()` requires a named rounding rule.
`allocate()` splits without losing a kobo (largest-remainder). 26 tests.

## 2. Results

**Corpus:** 439 payments over 2024-05-01 → 2024-05-31, ₦37,181,750.67, seed
`20240517`. Channels: 248 bank transfer, 115 card, 39 cash, 37 DVA.

| Layer | Resolved | Share | Correct | Precision | Money |
|---|---:|---:|---:|---:|---:|
| `exact_reference` | 164 | 37.36% | 164 | 1.0 | ₦13,229,863.68 |
| `dva_attribution` | 25 | 5.69% | 25 | 1.0 | ₦2,531,547.25 |
| `amount_window` | 118 | 26.88% | 118 | 1.0 | ₦7,884,224.74 |
| `probabilistic` | 27 | 6.15% | 27 | 1.0 | ₦3,761,274.75 |
| sent to a person | 105 | 23.92% | — | — | ₦9,774,840.25 |

- `auto_clear_rate` **0.7608**, `precision` **1.0**, `recall` **0.801**,
  `wrong_auto_clears` **0** (334 closed cases)
- Layer mix: deterministic **0.6993**, probabilistic **0.0615**, human **0.2392**
- Money closed ₦27,406,910.42 / to a person ₦9,774,840.25

**Calibration** (390 held-out candidate rows, never trained on):
Brier **0.0219**, ECE **0.0242**. Method chosen: **Platt**. Dev-set Brier by
method: identity 0.0934, Platt 0.0516, isotonic 0.0526.

**Threshold: 0.85**, chosen on 87 development payments by 4-fold CV. Cost matrix:
review ₦60 (3 min @ ₦1,200/hr), wrong auto-clear ₦5,000 (120 min + ₦2,600
goodwill) — **83:1**.

**Queue:** 105 waiting, ₦9,774,840.25 at risk. First 40 (one evening at 3
min each) hold ₦8,901,126.00 = **91.06%** of the money. `precision_at_40` =
**0.875**. 89 arrive with a suggestion; 12 flagged as suspected repeats.

**Adversarial slice:** duplicates 0/12 closed, stranger payments 0/10 closed,
twin invoices 10/10 closed and all scored correct. Verdict string: *"no
adversarial case was closed wrongly."* See §3.7 — that twin number needs an
asterisk.

**Extraction** (rules only; 40 hand-labelled reports): 94.4% read completely
right, 100% of unreadable ones correctly refused, 100% amount accuracy, **0
wrongly read**, 1 wrongly refused. On the 10 written *after* the parser was
finished: 50.0% read right (2 readable, 1 refused), 0 wrongly read.

**Against manual:** 439 payments × 3 min = 21.9h / ₦26,340. With Reckon: 5.2h /
₦6,300. Saved ₦20,040. Stated caveat in the harness: assumes the human is never
wrong, so it's the pessimistic end.

## 3. Design decisions, and the case against each

`docs/DECISIONS.md` holds 12 entries, each with an explicit **Rejected**
alternative and a **What it costs**. The interesting ones, with pushback:

### 3.1 Integer kobo, not `Decimal`

Rejected `float` (obvious) *and* `Decimal`. Reasoning in the file: `Decimal`
permits `Decimal("0.005")`, a third of a kobo, which isn't a thing that exists.
Integers make the impossible unrepresentable.

> **"`Decimal` is the standard answer for money. Isn't this NIH?"**
> Fair. `Decimal` is exact and battle-tested. The counter is that exactness
> isn't the property being bought — *representability* is. Cost, stated in the
> file: every boundary needs explicit conversion. That's real friction, paid in
> one file with 26 tests.

### 3.2 Hand-written logistic regression, not scikit-learn

18 features, ~950 candidate rows. Reason given in `model.py`: fit, calibration
and scoring readable in one file; installs with no compiler; reproducible
anywhere.

> **"sklearn gives you `LogisticRegression`, `CalibratedClassifierCV` and
> `StratifiedKFold` for free, better tested than yours. Why reinvent it?"**
> Honest answer: it would have been less code and fewer bugs. And there *was* a
> real bug — the hand-rolled isotonic PAVA didn't pool tied scores, so 200 cases
> scored 0.9 of which half were right came back as "0.9 means certain." Caught by
> `tests/test_model.py::test_isotonic_recovers_the_actual_rates`, which is
> exactly the failure calibration exists to detect. That's a point *for* using
> sklearn. What the hand-rolled version bought: class-balancing, the
> tie-preference rule in §3.4, and the per-payment decision unit in §3.5 are all
> non-default behaviours that would have needed custom code around sklearn
> anyway.

### 3.3 Threshold by cross-validation, not a held-out slice

The repo started with a 50/25/25 split. That left **29 payments** to pick a
threshold on, where a line of 0.61 produced zero observed errors — and the same
line was wrong **15%** of the time on the full corpus. Switched to 4-fold CV over
all 87 dev payments.

> **"CV on 87 payments is still tiny. Is 0.85 meaningful to two decimals?"**
> No, and the README says so: *"At an 83-to-1 cost ratio you would want several
> hundred before trusting a line to two decimal places."* The defence is that CV
> is the honest way to spend a small corpus, not that the corpus is big enough.

### 3.4 Calibration prefers the smoother method on a near-tie

Isotonic won on Brier by ~0.001 and did it by collapsing every probability onto
six distinct values — every threshold from 0.6 to 0.99 cleared identical cases.
`calibration.py` now has `PREFERENCE = (identity, platt, isotonic)` and
`TIE_TOLERANCE = 0.01`.

> **"You picked the worse-scoring model. Isn't that fudging?"**
> It's choosing on a criterion the scoring rule can't see. A step function that's
> right on average scores fine and destroys the threshold sweep. The tolerance is
> a named constant and `make eval` prints all three Briers, so the trade is
> visible rather than buried.

### 3.5 Threshold chosen per *payment*, not per candidate row

Each payment has ~12 candidates, ≤1 correct, so row-wise the data is ~90%
negatives and "queue everything" looks nearly free. `best_per_payment()` collapses
to one row per payment carrying the best candidate's probability.

### 3.6 The probabilistic layer only closes 6.15%

At 83:1 you need to be wrong <1.2% of the time for an auto-clear to pay.

> **"6% is barely worth the complexity. Why not drop the model entirely?"**
> The strongest challenge in the repo. Defence: those 27 payments are
> ₦3,761,274.75 and all 27 were right; and the model's *other* job is ranking the
> 105 queued cases and attaching evidence — 89 of them arrive with a suggestion.
> Counter-counter: that ranking could plausibly be done with a much simpler
> score, and the repo never tested that. Genuine open question.

### 3.7 The twin-invoice case, and why its 10/10 needs an asterisk

Two identical invoices, same customer, same amount, same day; one payment. The
answer key marks both references as **alternatives** — naming either is scored
correct. The deterministic layer refuses these (two candidates isn't certainty;
`tests/test_deterministic_on_corpus.py::test_layer_one_refuses_every_twin_invoice`
pins that). The probabilistic layer then closes all 10.

> **"So you scored 100% on your hardest adversarial case by making either answer
> count. Isn't that grading yourself leniently?"**
> Partly, yes — and it's worth stating plainly. The justification is that for
> two genuinely identical invoices from one customer, marking either paid leaves
> the books correct, so it isn't a coin-flip with a wrong side. The counter is
> that it *would* matter if the two invoices differed in anything the matcher
> can't see (a due date, a delivery). The label was changed mid-project from
> `winnable_by: "human"` to `"fuzzy"` after observing that layer one already
> declined them — i.e. the answer key was revised after seeing behaviour, which
> is exactly the move that deserves scrutiny. The change is in commit `600b8b8`
> and the reasoning is written into `generate.py::_twin_orders`.

### 3.8 Corpus generated, answer key shipped

Rejected: a hand-written fixture file (too small, too tidy — contains only the
cases you thought of) and anonymised real data (not ours to publish).

> **"Generated data means you tested against your own assumptions."**
> Correct, and it's the repo's biggest stated weakness. Mitigations actually
> present: the scenario weights are one named table (`SCENARIOS` in
> `generate.py`) rather than scattered; 26 property tests in `tests/test_corpus.py`
> assert the corpus contains what it claims; and two answer leaks were found and
> fixed (§4).

### 3.9 SQLite by default, Postgres by URL

One `RECON_DATABASE_URL`, no dialect-specific types. The round-trip bug in §4
was caught *because* of this choice, not despite it.

## 4. What broke, with evidence

The history is 36 commits, **8 of them `fix:`**, each with a body naming the
cause. This is a real trail, not a reconstructed one.

| Commit | What broke |
|---|---|
| `e90bfda` | Piping `mypy` through `tail` masked its exit code; a red commit landed. Fix added `scripts/check.sh` with `set -euo pipefail`. |
| `154dea6` | Two `mypy` installs on PATH; bare `mypy` resolved to one that couldn't see project deps. Fixed by `python -m` for every tool. |
| `31cd5c4` | **SQLite silently dropped timezones** (comparing a stored time to a fresh one raised) and `String` columns returned enums as `str`, breaking identity checks. Fixed with a `UtcDateTime` `TypeDecorator` and typed `Enum` columns. Would have behaved differently again on Postgres. |
| `a1437bc` | **Answer leak:** cash rows carried the customer's *real* name, making cash trivially matchable and flattering every coverage number. |
| `12e3b3a` | **Duplicate guard too narrow:** it only fired once the first payment had settled something, so a duplicate of an *ambiguous* payment sailed through and the pair quietly settled both of a customer's twin invoices. |
| `1aacb02` | **Jinja templates missing from the wheel** — container would start clean and 500 on first `/review`. Caught by installing the wheel into a bare virtualenv, not by any unit test. |
| `78b06e7` | A guard test tripped on `sk_live_` appearing inside an explanatory comment. |
| `6b8574a` | **Threshold overfit:** a 29-payment holdout showed 0 errors at 0.61; the same line was 15% wrong on the full corpus. Replaced with 4-fold CV (§3.3). Commit body states it outright. |

Two more failures are recorded in code/docs rather than a `fix:` commit:

- **Background-task ordering.** Starlette runs `BackgroundTasks` *before* a
  yielded dependency's teardown, so a request-scoped session hadn't committed
  when the worker went looking for the row. Measured directly, then fixed by
  committing in the handler's own `session_scope()`. Written up as DECISIONS #3.
- **Isotonic tie-pooling** (§3.2), caught by a calibration test.

## 5. Known limitations

Stated as the README states them, not softened:

- **Cash cannot be verified.** No provider record, no bank record. Marked
  attested, not verified. If someone pockets ₦20,000 and records ₦15,000 it
  reconciles cheerfully and is wrong.
- **The numbers describe a simulation.** Generated corpus; the scenario weights
  are guesses. If they're wrong, every percentage moves.
- **The threshold was chosen on 87 payments.**
- **100% precision will not survive real data.** Zero wrong clears on 334 cases
  is real on this corpus and an unrealistic expectation elsewhere.
- **Nothing retrains itself.** Rejection labels come out of `/api/labels` in
  training shape; a human must run it. Deliberate.
- **No age escalation in the queue.** Ordering is purely by money, so a small
  old case never surfaces.
- **Settlement batches come from the corpus, not Paystack's settlement
  endpoints.** Not built.
- **The model extraction layer has never been run against the real API.** It's
  implemented and tested against a stubbed client; `make eval-llm` needs a key.
  Every figure above is deterministic + logistic only.
- **One report in the labelled set is left failing** — a comma-separated list
  with no verb ("invoice 42: forty-five thousand naira, Ada Okonkwo, cash") —
  rather than special-cased.
- **Only one provider adapter exists.** The "provider-agnostic core" seam has
  never been tested by a second implementation.
- **Single process, in-memory workspace** (`state.py`). Review decisions don't
  survive a redeploy on ephemeral storage.
- **The container image has not been built.** No Docker daemon on the dev
  machine. What *was* verified: the wheel installed into a clean virtualenv with
  no source tree, started via the Dockerfile's exact command, and
  `scripts/smoke.py` passed against it. The base image layer is unproven; the
  Cloud Build config refuses to deploy until the same smoke test passes against
  a real container.

**One discrepancy to flag:** the README's `Live instance:` line still reads *"not
deployed yet."* A Railway deployment exists and `/review` has been confirmed to
load. The line is stale.
